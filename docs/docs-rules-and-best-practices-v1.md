# Documentation

## Structure

- The code git repository has a folder named `/docs` - this is the place we keep the documentation. Subfolders possible if grouping of certain featue docs together helps to structure the docs.
- We document in Markdown format .md files. These .md files are describing how certain features / classes / modules work.
- The files are versioned. We follow Semantic Versioning here - but without the patch version as we do not need that for docs.
- File names are following the pattern in `/docs` folder: "<name of the thing>-v<major>.<minor>.md"

## Companion docs

Planning documents.
Please read [planning-documents-v1.md](../coding/planning-documents-v1.md) to understand what they are!

## Rules to keep

When crafting / modifying a file stored here keep the following rules:

- Make sure we have header / meta data on the top of the file where we:
  - put in the generation / last modified date and time
  - always state clearly: "This doc was generated by AI agent"
- It is important that all versions of the same feature / module documentation (same file name without the version postfix - see above) must be self contained.
  This means the user can only open the latest version and gets every important info. No need to read the previous versions.
- In the beginning of each files we always document what has changed / what is new compared to the previous version. Create kinda changelog compared to the previous versions.
  But then all other information like TLDRs or describing how this/that works should be inherited from the previous version of the doc so it becomes self contained.
  Of course except what changed... Obviously.
- It is OK to refer in the companion planning document (plan.md file - see above) which was used to plan and describe the change.
  Then user can read and understand better "why" and "how" we did the change.
- We prefer bulleted lists over tables in natural situations.
  For example: changelog, meta data, parameter descriptions, etc. Use tables in the .md files only when it really makes sense or explicitly asked.
